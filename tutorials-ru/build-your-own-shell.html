1. Зачем писать свой шелл?

Шелл — сердце Unix; это клей, который удерживает вместе все маленькие инструменты Unix. Его понимание проясняет многие важные идеи Unix, а лучший путь к этому пониманию — написать собственный шелл. У воркшопа три цели:

  • Лучшее понимание процессов Unix — оно сделает вас лучше в проектировании и понимании программного обеспечения, работающего на Unix.
  • Разбор распространённых заблуждений о POSIX-шеллах — это сделает вас эффективнее в использовании и скриптовании с распространёнными шеллами вроде bash.
  • Создание работающей реализации шелла — шелла, о продолжении работы над которым вы действительно можете волноваться; на своём шелле можно делать бесконечно много личных доработок.
«Все разбитые шеллы… очень много разбитых шеллов… в наших ракушечных холмах» — из песни «Shellmounds» группы Grayceon; воркшоп назван в честь неё.

2. Как пользоваться репозиторием?

Материалы разбиты на прогрессивные этапы (Stages), каждый из которых покрывает почти самостоятельную тему. Каждый этап включает: описание изучаемых возможностей, список man-страниц, которые стоит посмотреть, и набор тестов. В корне репозитория есть скрипт validate, прогоняющий все тесты против вашего строящегося шелла — просто передайте путь к исполняемому файлу:

bash$ ./validate ../mysh/mysh

Можно запустить отдельный этап или даже один тест:

bash$ ./validate ../mysh/mysh stage_2
$ ./validate ../mysh/mysh stage_3 03

Для запуска тестов нужны expect и компилятор C. Тесты предполагают, что вы строите шелл семейства Борна с влиянием ksh. Любопытно, что bash и ksh должны проходить все тесты (проверьте через ./validate /bin/bash), а cat должен падать на всех! dash проходит всё, кроме этапа 5.

Этапы:

  • fork/exec/wait — основы процессов Unix и простейший возможный шелл.
  • Файлы и каналы — добавление каналов и переопределения файловых дескрипторов (fd).
  • Управление заданиями и сигналы — поддержка ^C, ^\ и ^Z.
  • Кавычки и подстановка (Expansion) — окружение, переменные, glob и часто неверно понимаемые понятия шелла.
  • Интерактивность — шлифовка шелла для повседневной интерактивной работы.

3. Этап 1: fork / exec / wait

На этом этапе вы знакомитесь с процессом Unix: запуск программы означает создание нового процесса (fork), превращение его в нужную программу (exec) и ожидание завершения (wait). Простейший возможный шелл — это цикл:

c#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    char *line = NULL;
    size_t capacity = 0;

    for (;;) {
        printf("mysh> ");
        if (getline(&line, &capacity, stdin) < 0)
            break;

        pid_t pid = fork();
        if (pid == 0) {
            /* дочерний: превращаем себя в программу */
            execlp(line, line, (char *)NULL);
            perror("exec");
            _exit(127);
        }
        /* родитель: ждём дочернего */
        wait(NULL);
    }
    return 0;
}

Замечания по этапу: fork возвращает в дочернем 0, а в родителе — идентификатор дочернего; exec* превращает текущий процесс (при успехе не возвращается); а wait останавливает родителя, пока дочерний не завершится. Воркшоп отмечает: для удовольствия сначала назовите свой шелл и сделайте ему собственное приглашение.

4. Этап 2: файлы и каналы

Здесь добавляются переопределение файловых дескрипторов и каналы. Файловые дескрипторы (fd) — целые числа, указывающие на открытые файлы; 0 = стандартный ввод, 1 = стандартный вывод, 2 = стандартная ошибка. Канал создаёт два fd, и всё, что записывается в один, читается из другого:

cint pipe_fds[2];
pipe(pipe_fds);   /* предположим, вернёт [4, 5] */

/* всё, что записано в 5, читается из 4 */

Для выполнения ls | wc: создай канал, сделай fork дважды (один для ls, один для wc), в первом дочернем dup2(pipe_fds[1], 1) (стандартный вывод = записывающий конец канала), во втором дочернем dup2(pipe_fds[0], 0) (стандартный ввод = читающий конец канала), а в родителе закрой оба конца. Переопределение fd делается через dup2:

c/* в дочернем на стороне ls: подключаем стандартный вывод к записывающему концу канала */
dup2(pipe_fds[1], STDOUT_FILENO);
execvp("ls", args_ls);
/* в дочернем на стороне wc: подключаем стандартный ввод к читающему концу канала */
dup2(pipe_fds[0], STDIN_FILENO);
execvp("wc", args_wc);
/* в родителе: */
close(pipe_fds[0]);
close(pipe_fds[1]);

«Перенаправление в файл» (> и <) делается теми же dup2 и open — так что после этапа 2 вы сможете выполнить и grep shel /usr/share/dict/words > /tmp/shel_words.

5. Этап 3: управление заданиями и сигналы

На этом этапе вы знакомитесь с сигналами и управлением заданиями. При нажатии ^C процессу приходит SIGINT; по умолчанию он убивает процесс. Но в интерактивном шелле этот сигнал должен достигать только исполняемого процесса, а не самого шелла. Ключевые моменты:

  • Шелл должен работать в отдельной группе процессов (process group) через setpgid и отдавать терминал через tcsetpgrp.
  • Сигналы ^C (SIGINT), ^\ (SIGQUIT) и ^Z (SIGTSTP) шелл должен игнорировать для себя, но передавать дочерним.
  • Через waitpid с флагом WNOHANG можно узнавать о завершении заданий, а SIGCHLD сообщает шеллу о завершении дочернего.
  • Управление заданиями означает поддержку ^Z и fg/bg/jobs: помещайте процессы в их собственную группу при создании и через tcsetpgrp определяйте, какая группа владеет терминалом.
c#include <signal.h>

/* шелл игнорирует терминальные сигналы для себя */
signal(SIGINT, SIG_IGN);
signal(SIGQUIT, SIG_IGN);
signal(SIGTSTP, SIG_IGN);

/* при выполнении задания:
   - дочерний проходит setpgid, чтобы создать собственную группу
   - родитель через tcsetpgrp отдаёт группе дочернего владение терминалом
   - после waitpid управление терминалом возвращается шеллу */

6. Этап 4: кавычки и подстановка

Этот этап проясняет часто неверно понимаемые понятия шелла: окружение (environment), переменные, globbing и кавычки. Основные моменты:

  • Подстановка переменных: $HOME через getenv разрешается в процессе шелла, и только затем происходит exec* — значит, этап 4 означает «подстановка до выполнения».
  • Globbing: *.c превращается самим шеллом через glob(3) в список файлов; дочерний видит только итоговые файлы.
  • Кавычки: '...', "..." и \ определяют, какие части подставляются, а какие нет — и, что интереснее, какие строки становятся «одним аргументом» (например, echo "a b").
  • Переменные окружения: VAR=value cmd создаёт временную переменную для одной команды; поскольку дочерний не может изменить окружение родителя, export должен быть встроенной командой.
c/* подстановка переменной до выполнения: */
char *val = getenv(name);
/* затем она попадает в argv */

/* glob до выполнения: */
glob_t g;
if (glob("*.c", 0, NULL, &g) == 0) {
    /* g.gl_pathv — итоговые аргументы */
}

7. Этап 5: интерактивность

Финальный этап шлифует шелл для повседневной интерактивной работы — вещи, которых не чувствуешь в неинтерактивном режиме: чтение и редактирование командной строки (строка ввода, автодополнение по Tab), приглашение, отражающее статус последней команды ($?), ^C в приглашении, которое должно очищать текущую строку, а не убивать шелл, и корректное объявление о завершении заданий. Именно эта часть, как настаивает воркшоп, делает работу по-настоящему приятной.

Замечание: если код на C где-то начинает вас изводить, воркшоп предлагает сначала начать с более высокоуровневого языка с хорошей поддержкой ОС (Python с os и subprocess, Ruby с Process, Rust с nix или даже OCaml/Scheme) — и на этапе 2 с Python не забудьте явно сделать дескрипторы файлов наследуемыми через os.set_inheritable(fd, True) (начиная с Python 3.4).

8. Куда дальше?

Для дальнейшего изучения воркшоп рекомендует: классическую книгу APUE (Стивенс), The Linux Programming Interface (Керриск), статью «Bourne-Again Shell» в архитектуре open-source программ, урок «Write a Shell in C» Стивена Бреннана (волна 3 этого же раздела!), книги об управлении заданиями в документации glibc и статьи о сигналах и управлении заданиями. И в конце: серия настоящих шеллов для чтения их кода — от busybox/ash и mksh до rc, zsh, fish и даже оригинального шелла Томпсона из истории Unix.

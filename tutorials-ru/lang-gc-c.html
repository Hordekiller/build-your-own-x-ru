Сборщик мусора на C (Baby's First Garbage Collector)

Зачем собирать GC вручную

Автоматическое управление памятью (сборка мусора) в таких языках, как Python, Java и даже JavaScript, — повседневная работа программистов; но когда вы пишете собственный интерпретатор, за вас объекты никто не подчистит. Боб Нистром в этой статье строит на C простой сборщик mark-and-sweep и показывает, что именно эта система считает «живым».

Главная идея: корни и граф объектов

В любом языке объекты, достижимые из «корней» (доступные переменные, стек вызовов и т.д.), — живые; остальные можно удалять. В этой статье для простоты предполагается, что корни — это «стек виртуальной машины»: связный список объектов, с которыми в данный момент работает интерпретатор.

У каждого объекта есть флаг marked. Сборщик работает в два этапа: разметка (начинается с корней и помечает все достижимые по графу ссылок объекты) и очистка (проходит по списку всех объектов и освобождает непомеченные).

Пример кода: структура объекта и функция сборки

Ctypedef struct sObject {
  struct sObject* next;   // связный список всех объектов
  char marked;            // флаг разметки
  union {
    int value;
    struct sObject* head; // для списков
    ...
  } data;
} Object;

void gc() {
  // 1) Разметка: от корней (стека VM)
  for (Object* root = vm.stack; root != NULL; root = root->next)
    mark(root);

  // 2) Очистка: освободи каждый непомеченный объект
  Object** obj = &vm.objects;   // указатель на весь список
  while (*obj != NULL) {
    if (!(*obj)->marked) {
      Object* unreached = *obj;
      *obj = unreached->next;
      free(unreached);
    } else {
      (*obj)->marked = 0;      // для следующего раза
      obj = &(*obj)->next;
    }
  }
}

Проблемы и практические решения

Главная проблема: когда VM использует новый объект, он ещё не привязан к стеку — в этом случае GC не должен его удалять. Решение статьи: объект «в процессе создания» прямо при создании помещается «на корень», чтобы его никогда не собрали.

Вторая проблема: в C можно игнорировать другие риски (например, корни на C-стеке), потому что тесты и примеры работают с кучей. В конце статьи упоминаются и «реальные» пути: conservative GC и exact GC, использование shadow stack или ручной оптимизации.

Итог

Эта статья за час чтения перекрывает путь «от почти нуля до настоящего GC»: меньше чем на 100 строках C вы строите систему управления памятью вашего интерпретатора и понимаете, почему языки высокого уровня так настаивают на «сборке мусора».

Простой сборщик мусора на C

Оригинальный источник: «Writing a simple garbage collector in C»

Цель урока

Когда вы пишете интерпретатор своего языка, вместо опоры на сырые malloc / free можно построить собственный сборщик мусора. Этот урок на технике mark-and-sweep показывает, как реализовать на C маленький и рабочий GC — ровно то, что делают настоящие интерпретаторы.

Проектирование: управляемые блоки

Главная идея: все выделенные объекты хранятся в связном списке «блоков». У каждого блока (с метаданными MAP_ENTRY): размер, адрес реальной памяти и флаги для разметки. Выделение выполняется через map_alloc, который создаёт блок и добавляет его в список.

Чтобы GC знал, что является «корнями», урок использует глобальный стек: когда хотите, чтобы переменная осталась «живой», кладёте её на этот стек через map_stack_push; GC начинает разметку оттуда.

Пример кода: структура блока и цикл sweep

Ctypedef struct map_entry {
  size_t      size;     // размер блока
  char*       memory;   // реальная память
  struct map_entry* next;
  uint8_t     marked;   // флаг разметки
} map_entry_t;

// Очистка: освободи все непомеченные блоки
void gc_sweep(void) {
  map_entry_t** entry = &map.entries;   // указатель на голову списка
  while (*entry) {
    map_entry_t* cur = *entry;
    if (!cur->marked) {                 // мусор найден!
      *entry = cur->next;
      free(cur->memory);
      free(cur);
    } else {
      cur->marked = 0;                 // для следующего цикла
      entry = &cur->next;
    }
  }
}

Важнейший технический приём статьи — указатель на указатель (map_entry_t**), позволяющий просто удалять элементы из связного списка без отдельной переменной-предшественника.

Шаги реализации

1) Построение map_alloc с правильным выравниванием (alignment) для типов C; 2) стек корней и map_stack_push; 3) функция gc_mark, рекурсивно обходящая ссылочные объекты (например, массивы); 4) gc_sweep и очистка; 5) тест программой с циклом выделений.

Автор также упоминает ограничения: этот GC «пассивный» (работает только при вызове), и для реальной работы (например, в интерпретаторе) нужны другие стратегии — метапрограммирование или консервативное сканирование.

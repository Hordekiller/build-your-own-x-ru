Создание простого Single Sign On (SSO) сервера на Node.js

Проблема SSO

У организации несколько приложений: почта, календарь, внутренняя система. Пользователь не хочет входить в каждое заново. Решение: центральный сервер аутентификации — пользователь логинится один раз, а остальные приложения узнают его автоматически.

В простейшей форме (из этого урока): SSO-сервер хранит сессию, приложения подключаются по «случайному токену», а список разрешённых приложений записан на сервере.

Поток входа

Когда пользователь приходит в приложение B без сессии, его редиректит на SSO-сервер. Если и там нет сессии, он видит форму логина; после успешного входа сервер возвращает его в B с кукой, и B должен подтвердить этот токен у сервера:

javascript// На SSO-сервере: проверка токена, присланного приложением
app.post('/validate', (req, res) => {
  const { appId, token } = req.body;

  // Это приложение разрешено? Токен валиден?
  const session = sessions[token];
  if (!apps.includes(appId) || !session) {
    return res.status(401).json({ error: 'Недействительно' });
  }

  // Возвращаем только идентификатор пользователя, не пароль!
  res.json({ ok: true, userId: session.userId });
});

Важный момент безопасности: приложения обмениваются только токеном; пароль и лишние данные им никогда не отправляются.

Сторона приложения

Каждое приложение знает, где живёт SSO (общая зона домена или кука). Логика приложения проста: если у нас нет сессии пользователя — редирект в SSO; с app.validate проверяем статус:

javascript// В каждом приложении: middleware для проверки входа
function requireSSO(req, res, next) {
  if (req.cookies.sso_token) {
    // Подтверждаем токен у SSO-сервера
    return ssoServer.validate(req.cookies.sso_token)
      .then(userId => { req.userId = userId; next(); })
      .catch(() => res.redirect(`${SSO_URL}/login?next=${req.path}`));
  }
  res.redirect(`${SSO_URL}/login?next=${req.path}`);
}

Параметр next важен: после входа пользователь возвращается именно на ту страницу, которую хотел, а не всегда на главную.

Границы упрощения

Это решение отлично для обучения; но для продакшена токены должны подписываться (HMAC/JWT), сессии храниться в Redis, поток должен быть защищён от CSRF и timing-атак, и лучше использовать стандарты OIDC/SAML. Поняв эту простую версию, читать документацию OIDC гораздо легче.

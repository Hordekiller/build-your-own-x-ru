Проблема синхронизации данных

Заметки, календарь, список покупок — всё это «общие данные», которые должны совпадать на нескольких устройствах. Первый способ — отправлять дельты на центральный сервер (как в простом CRDT). Проблема: когда два устройства вносят изменения офлайн, кто побеждает? Ответ CRDT: слияние без конфликтов, всегда согласованное.

Что такое CRDT?

CRDT (Conflict-free Replicated Data Type — тип данных без конфликтов) — структура, у которой каждое устройство имеет собственную локальную копию; изменения хранятся явными «атомами» (с версией и идентификатором устройства), а слияние двух состояний всегда даёт один и тот же результат — независимо от конфликтов. Текст, который несколько человек редактируют одновременно в Google Docs, — тому пример.

Yjs: готовый CRDT

Yjs — CRDT-библиотека для JS, поддерживающая текст, массив и Map. Идея урока: «движок синхронизации», в котором Node-сервер — только «центр событий»: просто ретранслирует изменения между клиентами (relay), не зная, что там за контент:

javascriptconst Y = require('yjs');
const ws = require('ws');

// Общий документ на сервере
const doc = new Y.Doc();

// Когда клиент прислал изменения, отдаём их остальным
function handleMessage(conn, data) {
  Y.applyUpdate(doc, data);          // слияние изменения на сервере
  broadcast(doc);                    // рассылка нового состояния всем
}

// Только что подключившийся клиент получает полное состояние, не дельту
function onConnect(conn) {
  conn.send(Y.encodeStateAsUpdate(doc));   // state sync
}

Паттерн «state sync + update sync» — это и есть протокол Yjs: сначала полное состояние, потом только дельты — точно как первичная настройка синхронизации.

Почему это интересно?

С таким движком возможна offline-first синхронизация для любого приложения: изменения сохраняются локально на устройстве и сразу после подключения отправляются и сливаются. Без CRDT проблему «победитель последней записи» и сложное версионирование пришлось бы решать вручную.

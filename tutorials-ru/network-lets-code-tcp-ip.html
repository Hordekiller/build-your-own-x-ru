Введение в серию

Написать собственный TCP/IP-стек на первый взгляд страшно: за тридцать лет жизни TCP накопил множество спецификаций. Но ядро спецификации довольно компактно — важные части: разбор TCP-заголовка, машина состояний, контроль перегрузки и вычисление Retransmission Timeout. Протоколы Ethernet (уровень 2) и IP (уровень 3) по сравнению со сложностью TCP гораздо проще.

В этой серии блог-постов мы реализуем минимальный TCP/IP-стек в пространстве пользователя (userspace) для Linux. Цель чисто учебная: глубже понять сети и системное программирование. Полный код проекта на GitHub: saminiir/level-ip.

Устройства TUN/TAP

Чтобы перехватывать низкоуровневый трафик из ядра Linux, мы используем устройство TAP. Одним словом, устройства TUN/TAP позволяют сетевым программам напрямую манипулировать трафиком уровня L3 (TUN) и L2 (TAP). Известный практический пример — туннелирование, где один пакет упаковывается внутрь payload другого (как в OpenVPN). Так как мы строим стек с уровня 2 и выше, нам нужен TAP:

c/* Из Kernel Documentation/networking/tuntap.txt */
int tun_alloc(char *dev)
{
    struct ifreq ifr;
    int fd, err;

    if( (fd = open("/dev/net/tap", O_RDWR)) < 0 ) {
        print_error("Cannot open TUN/TAP dev");
        exit(1);
    }

    CLEAR(ifr);

    /* Флаги:
     *   IFF_TUN - устройство TUN (без ethernet-заголовка)
     *   IFF_TAP - устройство TAP          ← нам нужно это
     *   IFF_NO_PI - не добавлять информацию о пакете впереди */
    ifr.ifr_flags = IFF_TAP | IFF_NO_PI;
    if( *dev ) {
        strncpy(ifr.ifr_name, dev, IFNAMSIZ);
    }

    if( (err = ioctl(fd, TUNSETIFF, (void *) &ifr)) < 0 ){
        print_error("ERR: Could not ioctl tun: %s\n", strerror(errno));
        close(fd);
        return err;
    }

    strcpy(dev, ifr.ifr_name);
    return fd;
}

После этого возвращённый дескриптор файла fd можно использовать для чтения и записи в буфер ethernet виртуального устройства. Флаг IFF_NO_PI критичен — без него перед ethernet-кадром добавляется лишняя информация о пакете (это можно проверить и в исходниках драйвера tun в ядре).

c/* Чтение и разбор кадра, полученного с устройства TAP */
if (tun_read(buf, BUFLEN) < 0) {
    print_error("ERR: Read from tun_fd: %s\n", strerror(errno));
}

struct eth_hdr *hdr = init_eth_hdr(buf);

handle_frame(&netdev, hdr);

Формат ethernet-кадра

Разнообразные технологии Ethernet — опора связи компьютеров в локальных сетях (LAN). Стандарт Ethernet сильно эволюционировал с первой версии, выпущенной Digital Equipment Corporation, Intel и Xerox в 1980 году. Первая версия работала на 10 Мбит/с и полудуплексной связи; поэтому понадобился протокол доступа MAC под названием CSMA/CD для упорядочивания потока данных. Позже 100BASE-T с витой парой сделал возможной полнодуплексную связь и большие скорости, а распространение ethernet-коммутаторов во многом устарело CSMA/CD. Стандарты Ethernet поддерживаются рабочей группой IEEE 802.3.

Заголовок ethernet-кадра можно структурировать на C следующим образом:

c#include <linux/if_ether.h>

struct eth_hdr
{
    unsigned char dmac[6];      /* MAC назначения */
    unsigned char smac[6];      /* MAC источника */
    uint16_t ethertype;         /* тип или длина payload */
    unsigned char payload[];    /* в нашем случае: IPv4 или ARP */
} __attribute__((packed));
  • dmac и smac: MAC-адреса сторон соединения.
  • ethertype: двухбайтовое поле «нагрузки»: если значение больше или равно 1536 — говорит тип payload (например, IPv4 или ARP), если меньше — длину payload.
  • После поля типа могут быть теги VLAN и QoS — в этой реализации опущены.
  • Если длина payload меньше минимальных 46 байтов, добавляются pad-байты.
  • В конце кадра — поле FCS для проверки корректности по CRC — в этой реализации игнорируется.

Атрибут packed говорит gcc не добавлять pad-байты для выравнивания данных. Причина — наш стиль разбора: простой каст типа на буфер:

cstruct eth_hdr *hdr = (struct eth_hdr *) buf;

Более переносимый (и более хлопотный) способ — «ручная сериализация» полей, чтобы компилятор не добавлял padding под выравнивание разных процессоров. Общий поток обработки входящего кадра прост: прочитать ← скастовать в eth_hdr ← handle_frame, который смотрит только на ethertype и по нему выбирает действие.

Протокол ARP и формат его сообщения

Протокол разрешения адресов (ARP) служит для динамического сопоставления 48-битного ethernet-адреса (MAC) с адресом протокола (например, IPv4). Ключевой момент: с ARP работают любые протоколы уровня L3 — не только IPv4; даже CHAOS с 16-битным адресом! Обычный сценарий: вы знаете IP-адрес сервиса в LAN, но для реальной связи нужен и аппаратный адрес (MAC); поэтому ARP вещает в сеть: «кто владеет этим IP, пусть объявит свой аппаратный адрес?»

cstruct arp_hdr
{
    uint16_t hwtype;    /* тип канального уровня; Ethernet = 0x0001 */
    uint16_t protype;   /* тип протокола; IPv4 = 0x0800 */
    unsigned char hwsize;   /* длина аппаратного адреса; 6 байт для MAC */
    unsigned char prosize;  /* длина адреса протокола; 4 байта для IP */
    uint16_t opcode;    /* 1=ARP request, 2=ARP reply, 3/4=RARP */
    unsigned char data[];   /* payload для IPv4 */
} __attribute__((packed));

struct arp_ipv4
{
    unsigned char smac[6];      /* MAC отправителя */
    uint32_t sip;               /* IP отправителя */
    unsigned char dmac[6];      /* MAC получателя */
    uint32_t dip;               /* IP получателя */
} __attribute__((packed));

Алгоритм разрешения адреса

Оригинальная спецификация (RFC 826) задаёт этот простой алгоритм:

textЕсть ли у меня тип оборудования ar$hrd?
Да:
  [Опционально: проверить и длину оборудования ar$hln]
  Говорю ли я по протоколу ar$pro?
  Да:
    [Опционально: проверить длину протокола ar$pln]
    Если пара <тип протокола, адрес протокола отправителя>
    уже есть в таблице перевода, обнови аппаратный адрес
    записи в соответствии с новой информацией.
    Я ли адрес протокола назначения (ar$tpa)?
    Да:
      Если запись новая, добавь тройку <тип протокола,
      адрес протокола отправителя, аппаратный адрес отправителя>
      в таблицу перевода.
      Является ли opcode запросом?  (теперь смотрим на opcode!)
      Да:
        Поменяй местами поля оборудования и протокола и
        помести локальные адреса в поля отправителя.
        Поменяй ar$op на REPLY
        Отправь пакет по (новому) адресу назначения.

Таблица перевода хранит результаты ARP, чтобы хосты могли напрямую проверять, есть ли запись, — это предотвращает заваливание сети повторными ARP-запросами. Полная реализация алгоритма — в файле arp.c проекта.

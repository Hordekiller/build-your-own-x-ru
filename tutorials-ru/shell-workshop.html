Мастерская шелла на C

1. Введение — на чём сосредоточен этот воркшоп?

Большинство из нас хоть иногда пользуется шеллом; некоторые проводят в нём большую часть времени. Часто мы воспринимаем его как должное и не знаем (и не задумываемся), как он делает свою работу. В этом воркшопе мы немного это исследуем, построив собственный шелл!

У шеллов очень много разных функций. Воркшоп сосредоточен на том, как запускаются процессы и как их ввод/вывод управляется каналами. Такие вещи, как подстановка переменных окружения и обработка сигналов, мы откладываем, но в конце дадим несколько направлений для продолжения.

Правило 0: в частности, нам совершенно не хочется возиться с кучей грязных деталей, включая (но не ограничиваясь):

  • Управление памятью
  • Парсинг/токенизация и прочая текстовая обработка
  • «Надлежащая» обработка ошибок

Поэтому функция parse_command и другие вспомогательные функции уже готовы за вас; сосредоточьтесь на самых полезных частях.

2. Начало: имя шелла и чтение ввода

Самое важное для старта — выбрать имя шелла и его приглашение! Автор во время подготовки воркшопа работал с heeee>; пример взаимодействия:

bashheeee> ls
shell   shell.c

Упражнение 1: настройте функцию main шелла так, чтобы она непрерывно получала от пользователя строку и пока просто печатала её — наш шелл — это «чуть более персональный cat»! Вот кусок для чтения строки в C в переменную line:

cchar *line = NULL;
int capacity = 0;
getline(&line, &capacity, stdin);

3. Системные вызовы

Теперь, когда мы умеем читать команду пользователя, нужно её выполнить. Для этого нужна помощь ядра — ядро отвечает за большинство вещей, связанных с процессами (плюс многое другое).

Способ, которым наши программы общаются с ядром, — системные вызовы; операции, при которых мы просим ядро сделать что-то за нас. Примеры:

  • Открытие файлов (open)
  • Чтение и запись в них (read, write)
  • Отправка и получение данных по сети (sendto, recvfrom)
  • Запуск программ (execve)

По сути, почти всё, что связано с взаимодействием наших программ с «реальным миром», включает системные вызовы. Сейчас нам интересен запуск программы; для этого используем вызов execve — и обёрточную функцию execvp.

4. Запуск программы и argv

Перед запуском программы нужно понять, как передаются её аргументы. Когда запускается программа, она получает массив аргументов, который традиционно называется argv. По соглашению, первый из них — имя программы. Поэтому при выполнении чего-то вроде ls -l /tmp argv, который получает ls, выглядит как { "ls", "-l", "/tmp" }.

c/* аргументы: { "ls", "-l", "/tmp" } */
char *argv[] = { "ls", "-l", "/tmp", NULL };
execvp("ls", argv);   /* если успешно, больше не возвращается */

Упражнение 2. Измените шелл так, чтобы после чтения строки из stdin он выполнял команду с её аргументами. Что-то неожиданное произошло?

Да — когда программа завершилась, вы не вернулись к приглашению; вас выкинуло прямо в основной шелл! Потому что вызов exec превращает текущий процесс в указанную команду. Процесс нашего шелла был заменён ls или тем, что вы выполнили. Когда та программа завершилась, процесс вышел — шелла больше нет!

5. fork: создание нового процесса

Чтобы этого избежать, хотим, чтобы команда выполнялась как новый процесс. Процессы создаются системным вызовом fork. Этот вызов создаёт новый процесс, который является копией существующего — вплоть до точки, где выполняется программа. Затем в этом новом процессе (дочернем) вызываем exec, и наш шелл остаётся для дальнейшего взаимодействия.

Возвращаемое значение fork говорит, где мы: в дочернем — 0, а в родителе возвращается идентификатор нового процесса.

cpid_t pid = fork();
if (pid == 0) {
    /* мы дочерние: превращаем себя в программу */
    execvp(argv[0], argv);
    /* сюда попадаем, только если exec не удался */
    perror("exec");
    exit(1);
}

Упражнение 3. Измените шелл так, чтобы он вызывал fork, а затем exec в дочернем. Поздравляем! Ваш шелл теперь почти полезен. Но есть одна неприятность: когда выполняется команда, приглашение, вероятно, печатается раньше вывода команды.

6. wait: ожидание дочерних процессов

Если посмотреть на код, видно, что родитель сразу возвращается к приглашению. Чтобы дождаться дочернего процесса, существует прекрасно названный системный вызов wait. Для наших целей достаточно вызвать его с аргументом NULL: wait(NULL);

Упражнение 4. Сделайте так, чтобы шелл вызывал wait для дочернего процесса перед возвратом к приглашению.

cpid_t pid = fork();
if (pid == 0) {
    execvp(argv[0], argv);
    perror("exec");
    exit(1);
}
wait(NULL);   /* родитель ждёт, пока дочерний завершится */

Теперь шелл ведёт себя как настоящий! Попробуйте несколько любимых команд. (Автор — фанат cowsay, но никто не мешает вам запустить ls или cat!)

7. Встроенные команды — почему не работает cd?

Что произойдёт, если мы захотим выполнить cd? Есть программа /bin/cd, которая должна сменить наш каталог; попробуйте эту последовательность:

bashheeee> pwd
/Users/kalmar/projects/conferences/2014/strangeloop/shell-workshop
heeee> cd ..
heeee> pwd
[что-то ... неожиданное?]
heeee> echo HEEEELLLPPPP!!!!!
HEEEELLLPPPP!!!!!

Эта последняя последовательность, вероятно, вас немного удивила. Чтобы понять, почему не удалось сменить каталог, нужно немного знать о работе процессов. У каждого процесса есть:

  • Собственная память (все глобальные и локальные переменные, стек и куча)
  • Дополнительные метаданные, которыми управляет ядро и которые процесс не может изменить напрямую — только через системные вызовы:
  • идентификатор пользователя (setuid)
  • идентификатор группы (setgid)
  • приоритет (setpriority)
  • рабочий каталог (chdir)

Итак, представьте, что мы делаем fork и exec процесса /bin/cd:

text1) Родитель: pid 1000, рабочий каталог /tmp
---- fork ----
2) Родитель: pid 1000, рабочий каталог /tmp
   Дочерний: pid 2000, рабочий каталог /tmp
---- exec `/bin/cd /home/awesome` в дочернем ----
3) Родитель: pid 1000, рабочий каталог /tmp
   Дочерний: pid 2000, рабочий каталог /tmp/awesome
---- дочерний выходит ----
4) Родитель: pid 1000, рабочий каталог /tmp

Процесс может изменить только собственное состояние — через системные вызовы; поэтому родительский процесс шелла по-прежнему имеет свой исходный рабочий каталог (/tmp).

Чтобы сменить каталог шелла, сам шелл должен вызвать chdir. Значит, шелл должен обрабатывать команду cd особым образом: если команда — cd, вместо обычного fork/exec вызывать chdir. То есть обработка cd встроена в сам шелл — это builtin!

cif (strcmp(cmd->name, "cd") == 0) {
    /* builtin: сам шелл меняет каталог */
    if (chdir(cmd->args[1]) != 0) {
        perror("chdir");
    }
} else {
    /* обычная команда: fork + exec + wait */
    ... 
}

Упражнение 6. Добавьте в свой шелл builtin cd.

cd — не единственная встроенная команда обычного шелла. Посмотрите через man builtin, что ещё есть. Заметьте: не все они обязаны быть встроенными; например, echo отлично работает и как внешняя команда, но многие шеллы держат её встроенной. Некоторые встроены ради производительности, ведь создание нового процесса имеет накладные расходы.

8. Каналы — файловые дескрипторы и dup2

Следующий шаг — реализация каналов. Попробуйте выполнить в своём шелле ls | wc:

bashheeee> ls | wc
ls: cannot access |: No such file or directory
ls: cannot access wc: No such file or directory

Пока он не знает, что | имеет особое значение, и пытается вывести списком файлы | и wc. Прежде чем это исправить, познакомимся с каналами поближе.

Файлы в системах Unix управляются файловыми дескрипторами. Если вы используете Linux, все файловые дескрипторы процесса видны через ls -l /proc/<pid>/fd. Файловые дескрипторы — целые положительные числа (0 = stdin, 1 = stdout, 2 = stderr и от 3 вверх — другие файлы, открытые процессом).

Вызов pipe создаёт два новых файловых дескриптора с особым свойством:

cint pipe_fds[2];
pipe(pipe_fds);  // например, кладёт [4, 5] в pipe_fds

Если pipe вернул [4, 5], всё, что записывается в 5, читается из 4. Значит, нужно сделать stdout ls равным 5, а stdin wc — равным 4. Способ изменить, куда указывает файловый дескриптор, — вызов dup2: в этом примере для ls нужен dup2(5, 1), а для wc — dup2(4, 0).

c/* Краткая схема построения канала ls | wc:
   1. Создай канал (предположим, fd 4 и 5)
   2. Сделай fork дважды (один для ls, один для wc)
   3. В дочернем 1: dup2(pipe_fds[1], 1), затем exec(ls)
   4. В дочернем 2: dup2(pipe_fds[0], 0), затем exec(wc)
   5. В родителе закрой оба конца канала */
c/* дочерний 1 (ls): стандартный вывод = записывающий конец канала */
dup2(pipe_fds[1], STDOUT_FILENO);
close(pipe_fds[0]);          /* закрой другой конец */
execvp("ls", args_ls);

/* дочерний 2 (wc): стандартный ввод = читающий конец канала */
dup2(pipe_fds[0], STDIN_FILENO);
close(pipe_fds[1]);
execvp("wc", args_wc);

Упражнение 7: напишите функцию вида fork_and_exec_with_io(cmd* cmd, int stdout_fd, int stdin_fd), которая делает fork и exec указанной команды и при необходимости меняет её stdin и stdout.

Упражнение 8: с помощью fork_and_exec_with_io реализуйте каналы из двух элементов.

9. Куда дальше?

Для продолжения есть два класса путей — естественное развитие и исследование других областей шелла:

Естественное развитие

  • Более длинные каналы: функция parse_line может вернуть любое количество команд с каналами — дальше дело за вами!
  • Перенаправление I/O в/из файлов: grep shel /usr/share/dict/words > /tmp/shel_words. Нужно расширить код парсинга для захвата этих перенаправлений; само перенаправление очень похоже на канал — только вместо pipe используется open для получения файлового дескриптора.
  • Перенаправление других дескрипторов: some-command 2>/tmp/errors означает «перенаправь stderr (fd 2) в /tmp/errors» — обобщение предыдущего случая.
  • Перенаправление в другие дескрипторы: some-command 2>&1 означает, что вывод stderr идёт туда же, куда и stdout, — дальнейшее расширение перенаправления.

Другие направления

  • Подстановка переменных окружения: сравните echo $HOME в своём шелле и в обычном; getenv находит переменную из окружения. Можно применять её во время или после парсинга.
  • Установка переменных окружения для дочерних процессов: TZ=Pacific/Samoa date — префикс VAR=value означает, что VAR установится только в окружении дочернего (setenv). Расширьте парсер.
  • Ещё один builtin: export — поскольку дочерний не может изменить окружение родителя, export должен быть встроенной командой.
  • Обработка сигналов: ^C посылает сигнал SIGINT; по умолчанию он уничтожает процесс. Установив обработчик сигнала, можно его перехватить или проигнорировать.
  • Globbing: wc -c * — раскрытие * делает сам шелл перед передачей аргумента дочернему; пригодится функция glob из <glob.h>.
  • Фоновый запуск: команда, заканчивающаяся на &, выполняется в фоне; шелл не вызывает wait.

Предыстория

Почти каждая программа в вебе работает поверх семейства коммуникационных стандартов, называемого Internet Protocol (IP). Член этого семейства, который важен нам, — это Transmission Control Protocol (TCP/IP), делающий общение между компьютерами похожим на чтение и запись файлов.

IP-программы общаются через сокеты. Каждый сокет — один конец канала связи точка-точка, примерно как телефон — один конец телефонного разговора. Сокет включает IP-адрес, идентифицирующий конкретную машину, и номер порта на этой машине. IP-адрес состоит из четырёх 8-битных чисел, например 174.136.14.108; система доменных имён (DNS) сопоставляет эти числа со знакомыми людям именами вроде aosabook.org.

Номер порта — число в диапазоне 0-65535, однозначно идентифицирующее сокет на машине-хосте. (Если IP-адрес — номер телефона компании, то номер порта — внутренний добавочный.) Порты 0-1023 зарезервированы для использования операционной системой; все остальные могут использовать оставшиеся порты.

Протокол передачи гипертекста (HTTP) описывает один из способов, которым программы могут обмениваться данными по IP. HTTP намеренно прост: клиент отправляет по сокетному соединению запрос, в котором указано, что он хочет, а сервер в ответ отправляет данные. Данные могут копироваться из файла на диске, динамически генерироваться программой или быть комбинацией того и другого.

Самое главное о HTTP-запросе: это просто текст. Любая программа, которая захочет, может его создать или разобрать. Но чтобы он был понятен, этот текст должен содержать части, показанные на рисунке ниже.

Метод HTTP почти всегда «GET» (получить информацию) или «POST» (отправить данные формы или загрузить файл). URL указывает, чего хочет клиент; часто это путь к файлу на диске, например /research/experiments.html, но (и это ключевой момент) решать, что с ним делать, — полностью дело сервера. Версия HTTP обычно «HTTP/1.0» или «HTTP/1.1».

HTTP-заголовки — пары ключ/значение, как эти три примера:

HTTPAccept: text/html
Accept-Language: en, fr
If-Modified-Since: 16-May-2005

В отличие от ключей хеш-таблиц, ключи в HTTP-заголовках могут появляться несколько раз. Это позволяет запросу указать, например, несколько типов принимаемого содержимого. Наконец, тело запроса — любые дополнительные данные, связанные с запросом; оно используется при отправке данных веб-форм, загрузке файлов и т.п. Между последним заголовком и началом тела должна быть пустая строка, показывающая конец заголовков. Заголовок с именем Content-Length говорит серверу, сколько байт читать в теле запроса.

HTTP-ответы форматируются так же, как HTTP-запросы: версия, заголовки и тело имеют ту же форму и смысл. Код состояния — число, показывающее, что произошло при обработке запроса: 200 означает «всё было хорошо», 404 — «не найдено», другие коды имеют другие значения. Фраза состояния повторяет ту же информацию в читаемом человеком виде, например «OK» или «not found».

Для этой главы об HTTP надо знать ещё только две вещи.

Во-первых, HTTP не сохраняет состояние (stateless): каждый запрос обрабатывается сам по себе, и сервер ничего не запоминает между двумя запросами. Если программе нужно отслеживать что-то вроде личности пользователя, она должна делать это сама. Обычный способ — файлы cookie: короткая строка, которую сервер отправляет клиенту, а клиент позже возвращает серверу. Когда пользователь делает что-то, требующее сохранения состояния в нескольких запросах, сервер создаёт новый cookie, сохраняет его в базе данных и отправляет браузеру. Каждый раз, когда браузер возвращает cookie, сервер использует его для поиска информации о действиях пользователя.

Во-вторых, URL может дополняться параметрами для передачи дополнительной информации. Это делается добавлением '?' к URL и затем пар 'key=value', разделённых '&'. Например, URL http://www.google.ca?q=Python просит Google найти страницы, связанные с Python. Стандарт кодирования URL показывает специальные символы через '%' и двухзначный код, а пробелы заменяет знаком '+'.

Открывать сокеты, составлять HTTP-запросы и разбирать ответы — нудно, поэтому большинство людей делает большую часть работы с библиотеками. У Python есть библиотека urllib2, но она выставляет на обозрение много деталей, до которых большинству людей нет дела. Библиотека Requests — более простая замена:

Привет, веб!

Теперь мы готовы написать наш первый простой веб-сервер. Основная идея проста:

  • дождаться, пока кто-то подключится к серверу и отправит HTTP-запрос;
  • разобрать этот запрос;
  • понять, чего он хочет;
  • получить эти данные (или сгенерировать динамически);
  • отформатировать данные как HTML; и
  • отправить их обратно.

Шаги 1, 2 и 6 одинаковы от программы к программе, поэтому стандартная библиотека Python содержит модуль BaseHTTPServer, делающий их за нас. Нам остаётся сделать шаги 3-5:

pythonimport BaseHTTPServer

class RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):
    '''Обработка HTTP-запросов возвратом фиксированной «страницы».'''

    # Страница, которую мы возвращаем
    Page = '''\
<html>
<body>
<p>Hello, web!</p>
</body>
</html>
'''

    # Обработка GET-запроса
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.send_header("Content-Length", str(len(self.Page)))
        self.end_headers()
        self.wfile.write(self.Page)

#----------------------------------------------------------------------

if __name__ == '__main__':
    serverAddress = ('', 8080)
    server = BaseHTTPServer.HTTPServer(serverAddress, RequestHandler)
    server.serve_forever()

Класс библиотеки BaseHTTPRequestHandler занимается разбором входящего HTTP-запроса и определением его метода. Если метод GET, класс вызывает метод do_GET. Наш класс RequestHandler переопределяет этот метод, чтобы создать простую страницу: текст хранится в переменной уровня класса Page, затем, после отправки кода ответа 200, заголовка Content-Type (говорящего клиенту интерпретировать данные как HTML) и длины страницы, возвращается клиенту.

Но RequestHandler — не вся история; для реального запуска сервера нужны последние три строки. Первая строка определяет адрес сервера как кортеж: пустая строка означает «запускайся на этой машине», а 8080 — порт. Затем создаётся экземпляр BaseHTTPServer.HTTPServer с этим адресом и именем класса обработчика запросов в качестве параметра, и его просят работать вечно (пока мы не убьём его Control-C).

Если запустить программу из командной строки, она ничего не показывает:

Bash$ python server.py

Если в браузере перейти на http://localhost:8080, мы увидим «Hello, web!», а в оболочке напечатается вот такой журнал:

Console127.0.0.1 - - [24/Feb/2014 10:26:28] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [24/Feb/2014 10:26:28] "GET /favicon.ico HTTP/1.1" 200 -

Первая строка проста: поскольку конкретный файл не запрашивался, браузер запросил «/». Вторая строка — потому что браузер автоматически отправляет второй запрос за файлом картинки /favicon.ico.

Раздача статических страниц

Очевидный следующий шаг — раздавать страницы с диска, а не генерировать их при запросе. Начинаем с переписывания do_GET:

python    def do_GET(self):
        try:

            # Понять, что именно запрошено
            full_path = os.getcwd() + self.path

            # ...не существует...
            if not os.path.exists(full_path):
                raise ServerException("'{0}' not found".format(self.path))

            # ...это файл...
            elif os.path.isfile(full_path):
                self.handle_file(full_path)

            # ...что-то, чем мы не управляем.
            else:
                raise ServerException("Unknown object '{0}'".format(self.path))

        # Обработка ошибок
        except Exception as msg:
            self.handle_error(msg)

Этот метод предполагает, что может раздавать любой файл в текущем каталоге или его подкаталогах (которые получает через os.getcwd). Он объединяет его с путём из URL (который библиотека автоматически кладёт в self.path и который всегда начинается с '/'), получая путь к файлу, который хочет пользователь. Если файла нет или это не файл, ошибка сообщается через выбрасывание и перехват исключения. Если путь ведёт к файлу, вызывается вспомогательный метод handle_file, который читает файл и возвращает его через send_content:

python    def handle_file(self, full_path):
        try:
            with open(full_path, 'rb') as reader:
                content = reader.read()
            self.send_content(content)
        except IOError as msg:
            msg = "'{0}' cannot be read: {1}".format(self.path, msg)
            self.handle_error(msg)

Обратите внимание: файл мы открываем в бинарном режиме, чтобы Python не пытался менять байтовые последовательности, похожие на окончания строк Windows. Также, чтение всего файла в память — плохая идея для многогигабайтных видеофайлов; управление этим выходит за рамки этой главы.

Для завершения класса пишем метод обработки ошибок и шаблон страницы с сообщением об ошибке:

python    Error_Page = """\
        <html>
        <body>
        <h1>Error accessing {path}</h1>
        <p>{msg}</p>
        </body>
        </html>
        """

    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content)

Эта программа работает, но только если не присматриваться. Проблема в том, что она всегда возвращает код состояния 200, даже когда запрошенной страницы не существует. Возвращаемая страница в этом случае содержит сообщение об ошибке, но браузер не понимает, что запрос на самом деле провалился. Чтобы это прояснить, надо изменить handle_error и send_content вот так:

python    # Обработка неизвестных объектов
    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content, 404)

    # Отправка реального содержимого
    def send_content(self, content, status=200):
        self.send_response(status)
        self.send_header("Content-type", "text/html")
        self.send_header("Content-Length", str(len(content)))
        self.end_headers()
        self.wfile.write(content)
Примечание: когда файл не найден, мы не выбрасываем ServerException, а строим страницу ошибки. ServerException предназначена для внутренней ошибки кода сервера — того, что неправильно сделали мы. Страница ошибки, создаваемая handle_error, появляется, когда пользователь попросил что-то неправильное, например URL файла, которого нет.

Списки каталогов

Следующий шаг: научиться показывать содержимое каталога, когда путь URL — это каталог. Можно пойти ещё на шаг дальше: искать в этом каталоге файл index.html и показывать список только если его нет.

Но встраивать эти правила в do_GET неправильно, потому что получившийся метод превратится в запутанный клубок операторов if, управляющих частными случаями. Правильное решение — отступить назад и решить общую задачу: понять, что делать с URL. Вот переписанный do_GET:

python    def do_GET(self):
        try:

            # Понять, что именно запрошено
            self.full_path = os.getcwd() + self.path

            # Понять, как это обрабатывать
            for case in self.Cases:
                handler = case()
                if handler.test(self):
                    handler.act(self)
                    break

        # Обработка ошибок
        except Exception as msg:
            self.handle_error(msg)

Первый шаг тот же: понять полный путь запрошенного объекта. Но после этого код сильно отличается. Вместо внутренних проверок эта версия проходит по набору case-ов в списке. Каждый case — объект с двумя методами: test, который сообщает, может ли он обработать запрос, и act, который реально что-то делает. Как только найден подходящий case, мы позволяем ему обработать запрос и выходим из цикла.

Вот три класса case, повторяющие поведение нашего прежнего сервера:

pythonclass case_no_file(object):
    '''Файл или каталог не существует.'''

    def test(self, handler):
        return not os.path.exists(handler.full_path)

    def act(self, handler):
        raise ServerException("'{0}' not found".format(handler.path))


class case_existing_file(object):
    '''Файл существует.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path)

    def act(self, handler):
        handler.handle_file(handler.full_path)


class case_always_fail(object):
    '''Базовый case, если ничего другое не сработало.'''

    def test(self, handler):
        return True

    def act(self, handler):
        raise ServerException("Unknown object '{0}'".format(handler.path))

и так строим список case-ов обработчика — над классом RequestHandler:

pythonclass RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):
    '''
    Если запрошенный путь ведёт к файлу, раздаётся этот файл.
    Если что-то идёт не так, создаётся страница ошибки.
    '''

    Cases = [case_no_file(),
             case_existing_file(),
             case_always_fail()]

    # ... остальное как раньше ...

Внешне это сделало сервер сложнее, а не проще: файл вырос с 74 строк до 99, добавился уровень косвенности без новой возможности. Польза проявляется, когда мы возвращаемся к задаче из начала главы: научить сервер раздавать страницу index.html для каталогов и показывать список каталога, если её нет. Вот обработчик первого случая:

pythonclass case_directory_index_file(object):
    '''Раздача страницы index.html для каталога.'''

    def index_path(self, handler):
        return os.path.join(handler.full_path, 'index.html')

    def test(self, handler):
        return os.path.isdir(handler.full_path) and \
               os.path.isfile(self.index_path(handler))

    def act(self, handler):
        handler.handle_file(self.index_path(handler))

Единственное необходимое изменение в RequestHandler — добавить объект case_directory_index_file в список Cases:

python    Cases = [case_no_file(),
             case_existing_file(),
             case_directory_index_file(),
             case_always_fail()]

А как насчёт каталогов без страницы index.html? Проверка та же с уместным not, но что должен делать метод act? Логически он должен построить и вернуть список каталога, но наш текущий код этого не позволяет: RequestHandler.do_GET вызывает act, но не получает и не обрабатывает возвращаемое значение.         try:
            entries = os.listdir(full_path)
            bullets = ['<li>{0}</li>'.format(e) 
                for e in entries if not e.startswith('.')]
            page = self.Listing_Page.format('\n'.join(bullets))
            self.send_content(page)
        except OSError as msg:
            msg = "'{0}' cannot be listed: {1}".format(self.path, msg)
            self.handle_error(msg)

Протокол CGI

Разумеется, большинство людей не хочет править исходники веб-сервера ради добавления возможностей. Поэтому серверы с самого начала поддерживали механизм под названием Common Gateway Interface (CGI), который даёт стандартный способ запускать внешнюю программу для удовлетворения запроса.

Например, предположим, мы хотим, чтобы сервер показывал локальное время на HTML-странице. Сделаем это в отдельной программе в несколько строк:

pythonfrom datetime import datetime
print '''\
<html>
<body>
<p>Generated {0}</p>
</body>
</html>'''.format(datetime.now())

Чтобы веб-сервер запускал эту программу для нас, добавим такой case-обработчик:

pythonclass case_cgi_file(object):
    '''Что-то исполняемое.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path) and \
               handler.full_path.endswith('.py')

    def act(self, handler):
        handler.run_cgi(handler.full_path)

Проверка проста: заканчивается ли путь файла на .py? Если да, RequestHandler запускает эту программу:

python    def run_cgi(self, full_path):
        cmd = "python " + full_path
        child_stdin, child_stdout = os.popen2(cmd)
        child_stdin.close()
        data = child_stdout.read()
        child_stdout.close()
        self.send_content(data)
Предупреждение: это сверхнебезопасно: если кто-то узнает путь к файлу Python на вашем сервере, вы просто позволите ему запустить его, не беспокоясь о том, к каким данным он получит доступ или о возможном бесконечном цикле. (Кстати, popen2 в новых версиях устарел в пользу модуля subprocess.)

Отложив это в сторону, основная идея проста:

  • запустить программу в подпроцессе;
  • забрать всё, что подпроцесс отправляет в стандартный вывод;
  • вернуть это запросившему клиенту.

Полный протокол CGI гораздо богаче — в частности, он позволяет параметры в URL, которые сервер передаёт запускаемой программе, — но эти детали не влияют на общую архитектуру системы... которая, опять же, начинает запутываться. У RequestHandler сначала был метод handle_file для содержимого. Теперь добавились два особых случая: list_dir и run_cgi. Этим трём методам здесь не место, поскольку в основном их используют другие.

Решение простое: создать родительский класс для всех case-обработчиков и перемещать в него методы только тогда, когда их используют два или более обработчика. Когда всё закончено, класс RequestHandler выглядит так:

pythonclass RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):

    Cases = [case_no_file(),
             case_cgi_file(),
             case_existing_file(),
             case_directory_index_file(),
             case_directory_no_index_file(),
             case_always_fail()]

    # Как показывать ошибку
    Error_Page = """\
        <html>
        <body>
        <h1>Error accessing {path}</h1>
        <p>{msg}</p>
        </body>
        </html>
        """

    # Классификация и обработка запроса
    def do_GET(self):
        try:

            # Понять, что именно запрошено
            self.full_path = os.getcwd() + self.path

            # Понять, как это обрабатывать
            for case in self.Cases:
                if case.test(self):
                    case.act(self)
                    break

        # Обработка ошибок
        except Exception as msg:
            self.handle_error(msg)

    # Обработка неизвестных объектов
    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content, 404)

    # Отправка реального содержимого
    def send_content(self, content, status=200):
        self.send_response(status)
        self.send_header("Content-type", "text/html")
        self.send_header("Content-Length", str(len(content)))
        self.end_headers()
        self.wfile.write(content)

а родительский класс для case-обработчиков — такой:

pythonclass base_case(object):
    '''Родитель case-обработчиков.'''

    def handle_file(self, handler, full_path):
        try:
            with open(full_path, 'rb') as reader:
                content = reader.read()
            handler.send_content(content)
        except IOError as msg:
            msg = "'{0}' cannot be read: {1}".format(full_path, msg)
            handler.handle_error(msg)

    def index_path(self, handler):
        return os.path.join(handler.full_path, 'index.html')

    def test(self, handler):
        assert False, 'Not implemented.'

    def act(self, handler):
        assert False, 'Not implemented.'

и обработчик существующего файла (просто как пример):

pythonclass case_existing_file(base_case):
    '''Файл существует.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path)

    def act(self, handler):
        self.handle_file(handler, handler.full_path)

Обсуждение

Различия между нашим исходным кодом и перестроенной версией отражают две важные идеи. Первая — смотреть на класс как на набор связанных служб. RequestHandler и base_case не принимают решений и не действуют; они предоставляют инструменты, которыми другие классы пользуются для выполнения этих действий.

Вторая — расширяемость: люди могут добавить новую возможность веб-серверу либо написав внешнюю CGI-программу, либо добавив класс case-обработчика. Второй способ требует однострочного изменения в RequestHandler (вставка case-обработчика в список Cases), но от него можно избавиться, читая файл конфигурации и загружая классы обработчиков из него. В обоих случаях они могут игнорировать большинство низкоуровневых деталей, точно так же, как авторы класса BaseHTTPRequestHandler позволили нам игнорировать детали управления сокетными соединениями и разбора HTTP-запросов.

Эти идеи полезны в целом; посмотрите, не найдёте ли вы способы применить их в собственных проектах.

Введение: что делает хороший воксельный движок?

Эта серия — не однострочный туториал, а путешествие постепенной разработки: «Эти уроки я писал, пока строил собственный воксельный движок — тот, что позже стал игрой Vox». Основная идея: воксельный движок нужно строить итеративно — начать с совсем простой вещи и шаг за шагом усложнять. Крупные задачи вроде управления чанками или обнаружения коллизий — каждая отдельная, независимо решаемая «задача».

Три главных и амбициозных цели хорошего воксельного движка глазами автора:

  • Эффективность (Efficient): возможность рендерить огромное число вокселей на экране в один момент.
  • Динамичность (Dynamic): движок должен уметь изменять любой воксель мира в любой момент (вкл/выкл, строить/ломать).
  • Масштабность (Expansive): общий масштаб мира должен быть велик и не ограничиваться произвольными рамками.

Структура данных блока

Первая техническая статья: каждый воксель — трёхмерный куб, фундамент всего движка. Поскольку каждый воксель мира уникален и игрок может его менять, каждый блок должен хранить собственные данные — но тут ключевой момент: каждый лишний байт на уровне блока раздувает объём хранилища целого мира из миллионов блоков. Что нужно хранить:

  • Флаг активности (active flag): блок включён или выключен; при рендере рисуются только активные блоки. Именно это делает мир динамичным.
  • Тип блока (block type): дерево, трава, земля, камень и т.д. — позже у каждого типа будут свой вид и поведение.

А что хранить не следует — важное правило «процедурной генерации»:

  • Позиция блока не требует хранения; она выводится из его индекса в массиве хранилища.
  • Нормали граней, текстурные координаты и цвет блока тоже не хранятся — всё получается из типа блока во время выполнения (вся трава одного цвета).

Это важное отличие от «традиционной 3D-модели»: в обычном меш-файле хранятся vertex, index, texcoord, normal и т.д.; а в вокселе хранится только минимум данных (active + тип), чтобы тот же мир можно было воссоздать из тех же данных.

Chunk: масштаб и управление миром

Блоки объединяются в единицы под названием Chunk (кубические куски мира). Ключевой момент статьи «Chunk Management»: управление состояниями чанков. Вместо простого списка автор держит несколько подсписков для разных состояний чанка:

  • ChunkLoadList: чанки, ожидающие загрузки — асинхронно и с ограничением числа за кадр (чтобы частота кадров не падала при загрузке).
  • ChunkSetupList: загруженные чанки, которым нужна настройка вокселей.
  • ChunkRebuildList: чанки, чьи воксели изменились и чьи меши нужно перестроить.
  • ChunkUnloadList: чанки, уходящие из поля зрения, для освобождения памяти.
  • ChunkVisibilityList: все чанки, которые потенциально могут быть видны.
  • ChunkRenderList: финальное подмножество для реального рендера после culling.

Поток обновления каждого кадра: 1) загрузка → 2) setup → 3) rebuild → 4) unload → 5) обновление списка видимости → 6) обновление списка рендера. Различие «списка видимости» и «списка рендера» ключевое: список видимости обновляется только когда камера пересекает границу чанка (оптимально), а список рендера выполняет на этом небольшом множестве тяжёлую работу — frustum culling и удаление пустых чанков.

Рендеринг: один вызов на чанк

Статья «Display Lists or Vertex Buffers» объясняет критичный принцип производительности: чтобы рендерить миллионы вокселей, нужно делать один вызов рендера на чанк, а не на куб. Сравниваются три способа 3D-рендера:

  • Непосредственный режим (immediate mode): отправка вызовов рендера по одному каждый кадр — убийственно для больших сцен.
  • Vertex Buffer: сбор данных треугольников в большой массив и единичная передача через glDrawElements/glDrawArrays — выбор автора.
  • Display List: хранение списка вызовов на GPU.

Построить буфер меша чанка просто: пройдись по активным блокам и добавь треугольники каждого куба в буфер; затем один вызов рендера рисует весь чанк. Но этот выбор влечёт важный компромисс: при изменении вокселя весь буфер меша этого чанка приходится перестраивать — поэтому размер чанка нужно выбирать разумно (больше = быстрее рендер, но дороже rebuild).

cpp// Построение буфера меша чанка: обход блоков и добавление треугольников активных блоков
for (size_t i = 0; i < m_blocks.size(); ++i) {
    if (m_blocks[i].IsActive()) {
        const glm::vec3 blockPos = Block_GetPosFromArray(i);
        CreateCube(vertexBuffer, blockPos);   // добавь треугольники куба
    }
}

Оптимизации рендеринга

Статья «Chunk Optimizations» знакомит с практичными оптимизациями:

  • Не рисовать невидимые треугольники: перед построением куба проверь шесть соседей (x±1, y±1, z±1); для любой грани, смежной с активным блоком, её треугольники не строятся. Это самая простая и действенная оптимизация.
  • Пропуск пустых чанков: флаг m_emptyChunk; чанк без активных блоков вообще не попадает в рендер.
  • Слияние граней (face merging): объединение смежных однотипных граней в один более крупный четырёхугольник — алгоритм сложнее, но очень эффективен.

Тип блока, текстура и цвет

Важное и честное проектное решение: автор в итоге отказался от текстур и добился стилизованного вида цветом и свойствами материалов. Если вы хотите текстуры, вы узнаете два ключевых момента:

  • Обязательно используйте Texture Atlas: все текстуры в одной; поскольку привязка текстуры — дорогая операция, одна привязка на весь чанк даёт огромную разницу.
  • Не храните текстурные координаты; генерируйте их на лету: у каждого типа блока фиксированный диапазон координат в атласе; он вычисляется из типа блока, а не читается с диска.

Обнаружение коллизий: без обхода всего мира

Статья «Collision Detection» несёт важную архитектурную мысль: поскольку мир полностью динамичен, никакое заранее вычисленное решение не работает — коллизии должны проверяться по актуальным данным мира. И чтобы не обходить (что невозможно!) все воксели:

  • Позиция игрока переводится в координаты воксельного пространства; тогда нужно проверить лишь 1 воксель под игроком — коллизия сводится к вопросу «активен ли этот воксель?».
  • Частицы = точки, существа = bounding box: частицы блоков симулируются как простые точки (дёшево), а крупные существа — с bounding box (высокая точность).
  • Пропущенные коллизии (missed collisions): очень быстрый объект за кадр может пролететь сквозь стену толщиной в куб; решение — многократная проверка коллизий за кадр: зная минимальную дистанцию прохода сквозь воксель, число проверок подбирается так, чтобы объект никогда не перепрыгнул воксель.
  • Отклик коллизии зависит от движения игрока: при падении — толкай наверх вокселя и не применяй гравитацию в этом кадре; при ходьбе — вычисляй вектор скольжения (slide vector) для движения вдоль стены.

Чему вы научитесь

  • Мышление «минимум данных на уровне блока» и процедурная генерация дорогих данных.
  • Архитектура чанков: асинхронная загрузка, состояния, разделение списка видимости и списка рендера.
  • Эффективный рендеринг: один вызов на чанк, удаление скрытых треугольников и слияние граней.
  • Эффективные коллизии: переход в воксельное пространство, точка против bounding box и решение пропущенных коллизий.
Дополнительное замечание: те же идеи (чанки, асинхронный rebuild, face culling и воксельные коллизии) лежат в основе современных движков вроде Minecraft-подобных. Движок автора серии превратился в настоящую игру Vox — доказательство, что такими же маленькими шагами можно дойти до реального продукта.

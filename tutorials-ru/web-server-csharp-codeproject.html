Введение

В этой статье по шагам задокументировано создание веб-сервера, чтобы вы почувствовали, как он строится с чистого листа: проектные и реализационные решения (хорошие и плохие) и весь процесс. Первый шаг процесса — заставить работать класс HttpListener. Дальше добавим немного логирования. Затем построим базовую структуру для нашего веб-приложения. Дальше реализуем простой механизм маршрутизации глаголов (verbs) и путей к обработчикам, займёмся аутентификацией и истечением сессий и выполним пару AJAX-запросов.

Текущая конфигурация поддерживает:

  • Маршрутизацию (Routing)
  • Менеджер сессий (Session Manager)
  • Авторизацию (Authorization)
  • Истёкшие сессии (Expired Sessions)

Поскольку веб-сервер очень лёгкий, автор посчитал совершенно излишним такое сложное дело, как реализация плагинов. Есть три основных файла:

  • Listener.cs — слушает через HttpListener и отвечает на соединения
  • Router.cs — управляет маршрутизацией
  • SessionManager.cs — управляет состоянием сессий соединений

Шаг 1 — HttpListener

Первый шаг — настройка класса HttpListener. Автор выбрал этот путь вместо низкоуровневых сокетов, потому что HttpListener предоставляет много полезных сервисов, например декодирование HTML-запроса. Веб-сервер реализуется как библиотека. На первом шаге веб-серверу нужно это:

csharpusing System.Net;
using System.Net.Sockets;
using System.Threading;

Поскольку веб-сервер по сути не имеет состояния (кроме объектов сессий), большую часть поведения можно реализовать в виде статических синглтонов:

csharpnamespace Clifton.WebServer
{
  /// <summary>
  /// Вёрткий и безжалостный веб-сервер.
  /// </summary>
  public static class Server
  {
    private static HttpListener listener;
    // ...

Исходное предположение — подключение к серверу во внутренней сети (intranet), поэтому берём IP-адреса локального хоста:

csharp/// <summary>
/// Возвращает список IP-адресов, назначенных устройствам локальной сети,
/// например проводному Ethernet, беспроводной сети и т.д.
/// </summary>
private static List<IPAddress> GetLocalHostIPs()
{
  IPHostEntry host;
  host = Dns.GetHostEntry(Dns.GetHostName());
  List<IPAddress> ret = host.AddressList.Where(ip => ip.AddressFamily == AddressFamily.InterNetwork).ToList();

  return ret;
}

Затем создаём экземпляр HttpListener и добавляем префиксы localhost:

csharpprivate static HttpListener InitializeListener(List<IPAddress> localhostIPs)
{
  HttpListener listener = new HttpListener();
  listener.Prefixes.Add("http://localhost/");

  // Слушай и IP-адреса
  localhostIPs.ForEach(ip =>
  {
    Console.WriteLine("Listening on IP " + "http://" + ip.ToString() + "/");
    listener.Prefixes.Add("http://" + ip.ToString() + "/");
  });

  return listener;
}

Позаимствовав идею из статьи «REST — A Simple REST framework», создаём семафор, ожидающий разрешённое число одновременных соединений:

csharppublic static int maxSimultaneousConnections = 20;
private static Semaphore sem = new Semaphore(maxSimultaneousConnections, maxSimultaneousConnections);

Это реализуется в рабочем потоке, вызываемом через Task.Run:

csharp/// <summary>
/// Начало прослушивания соединений в отдельном рабочем потоке.
/// </summary>
private static void Start(HttpListener listener)
{
  listener.Start();
  Task.Run(() => RunServer(listener));
}

/// <summary>
/// Начало ожидания соединений вплоть до "maxSimultaneousConnections".
/// Этот код выполняется в отдельном потоке.
/// </summary>
private static void RunServer(HttpListener listener)
{
  while (true)
  {
    sem.WaitOne();
    StartConnectionListener(listener);
  }
}

Наконец, реализуем слушатель соединений как ожидаемый (awaitable) async-процесс:

csharp/// <summary>
/// Ожидание соединений.
/// </summary>
private static async void StartConnectionListener(HttpListener listener)
{
  // Жди соединение. Пока ждём, верни управление вызывающему.
  HttpListenerContext context = await listener.GetContextAsync();

  // Освободи семафор, чтобы другой слушатель стартовал немедленно.
  sem.Release();

  // У нас есть соединение — сделаем что-нибудь...
}

Так и сделаем:

csharpstring response = "Hello Browser!";
byte[] encoded = Encoding.UTF8.GetBytes(response);
context.Response.ContentLength64 = encoded.Length;
context.Response.OutputStream.Write(encoded, 0, encoded.Length);
context.Response.OutputStream.Close();

Нужен и общий метод Start:

csharp/// <summary>
/// Запускает веб-сервер.
/// </summary>
public static void Start()
{
  List<IPAddress> localHostIPs = GetLocalHostIPs();
  HttpListener listener = InitializeListener(localHostIPs);
  Start(listener);
}

Теперь в консольном приложении можно запустить сервер:

csharpusing System;

using Clifton.WebServer;

namespace ConsoleWebServer
{
  class Program
  {
    static void Main(string[] args)

  }
}
Совет автора: всегда инспектируйте консоль браузера — это ваш друг, и он расскажет вам обо всех ошибках! Например, в этом тесте мы замечаем, что нужно следить за кодировкой, выполняемой в HTML: response = "<html><head><meta http-equiv='content-type' content='text/html; charset=utf-8'/></head>Hello Browser!</html>"

Шаг 2 — Логирование

Сначала добавим немного логирования — оно очень полезно, чтобы видеть, какие запросы приходят к нашему веб-серверу:

csharpLog(context.Request);

/// <summary>
/// Логирование запросов.
/// </summary>
public static void Log(HttpListenerRequest request)
{
  Console.WriteLine(request.RemoteEndPoint + " " + request.HttpMethod + " /" + request.Url.AbsoluteUri.RightOf('/', 3));
}

Вызов Log добавляем сразу после освобождения семафора. После добавления логгера сразу замечаем: браузер запрашивает не только страницу по умолчанию, но и favicon.ico! Надо что-то делать!

Шаг 3 — Раздача контента: маршрутизация по умолчанию

Очевидно, мы не хотим зашивать веб-страницы строками в C#. Поэтому строим базовую структуру для нашего веб-приложения — целиком на свой вкус: всё выводится из папки «Website», которая содержит такие подпапки:

  • Pages: корень всех страниц
  • CSS: все файлы .css и связанные
  • Scripts: все файлы .js
  • Images: все файлы изображений

Для базового поведения нужен начальный маршрутизатор. Первая версия отвечает только файлами из папки «Website» и подпапок — по пути URL и расширению запроса. Сначала извлечём кое-какую информацию из URL запроса:

csharpHttpListenerRequest request = context.Request;
string path = request.RawUrl.LeftOf("?"); // только путь, без параметров
string verb = request.HttpMethod; // get, post, delete и т.д.
string parms = request.RawUrl.RightOf("?"); // параметры URL идут после ?
Dictionary<string, string> kvParams = GetKeyValues(parms); // преобразуй в пары ключ-значение

Теперь можно отдать эту информацию маршрутизатору: router.Route(verb, path, kvParams);

Вместо switch-выражений (которые автор не любит) инициализируем словарь известных расширений и их загрузчиков. Учтите, как разные функции могут загружать контент, например из базы данных:

csharppublic class Router
{
  public string WebsitePath { get; set; }

  private Dictionary<string, ExtensionInfo> extFolderMap;

  public Router()
  {
    extFolderMap = new Dictionary<string, ExtensionInfo>()
    {
      {"ico", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/ico"}},
      {"png", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/png"}},
      {"jpg", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/jpg"}},
      {"gif", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/gif"}},
      {"bmp", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/bmp"}},
      {"html", new ExtensionInfo() {Loader=PageLoader, ContentType="text/html"}},
      {"css", new ExtensionInfo() {Loader=FileLoader, ContentType="text/css"}},
      {"js", new ExtensionInfo() {Loader=FileLoader, ContentType="text/javascript"}},
      {"", new ExtensionInfo() {Loader=PageLoader, ContentType="text/html"}},
    };
  }
  // ...

Заметим, что обрабатывается и случай «без расширения», где предполагается HTML-страница. Также задаётся content type — иначе в консоли браузера мы получим предупреждение «контент считается определённого типа». Наконец, показана функция, выполняющая собственно загрузку.

Загрузчик изображений

csharp/// <summary>
/// Читает файл изображения и возвращает ResponsePacket с сырыми данными.
/// </summary>
private ResponsePacket ImageLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  FileStream fStream = new FileStream(fullPath, FileMode.Open, FileAccess.Read);
  BinaryReader br = new BinaryReader(fStream);
  ResponsePacket ret = new ResponsePacket() { Data = br.ReadBytes((int)fStream.Length), ContentType = extInfo.ContentType };
  br.Close();
  fStream.Close();

  return ret;
}

Загрузчик файлов

csharp/// <summary>
/// Читает по сути текстовый файл и возвращает ResponsePacket с текстом в кодировке UTF8.
/// </summary>
private ResponsePacket FileLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  string text = File.ReadAllText(fullPath);
  ResponsePacket ret = new ResponsePacket() { Data = Encoding.UTF8.GetBytes(text), ContentType = extInfo.ContentType, Encoding = Encoding.UTF8 };

  return ret;
}

Загрузчик страниц

Загрузчику страниц нужно больше работы для обработки таких вариантов:

  • foo.com
  • foo.com\index
  • foo.com\index.html

Во всех сочетаниях лоад завершается файлом Pages\index.html:

csharp/// <summary>
/// Загружает HTML-файл; учитывает пропущенные расширения и IP/домен без файла,
/// которые должны возвращаться к index.html по умолчанию.
/// </summary>
private ResponsePacket PageLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  ResponsePacket ret = new ResponsePacket();

  if (fullPath == WebsitePath) // если после имени домена или IP ничего нет — загрузи index.html по умолчанию
  {
    ret = Route(GET, "/index.html", null);
  }
  else
  {
    if (String.IsNullOrEmpty(ext))
    {
      // расширения нет — добавляем ".html"
      fullPath = fullPath + ".html";
    }

    // вставляем папку "Pages" в путь
    fullPath = WebsitePath + "\Pages" + fullPath.RightOf(WebsitePath);
    ret = FileLoader(fullPath, ext, extInfo);
  }

  return ret;
}

У нас есть два вспомогательных класса, и после сборки всего вместе получается начальный маршрутизатор, возвращающий контент из файлов:

csharppublic ResponsePacket Route(string verb, string path, Dictionary<string, string> kvParams)
{
  string ext = path.RightOf('.');
  ExtensionInfo extInfo;
  ResponsePacket ret = null;

  if (extFolderMap.TryGetValue(ext, out extInfo))
  {
    // Убираем ведущий '/' и форматируем разделителем пути Windows
    string fullPath = Path.Combine(WebsitePath, path);
    ret = extInfo.Loader(fullPath, ext, extInfo);
  }

  return ret;
}

Нужен и финальный рефакторинг — убрать тестовый ответ и заменить его контентом, возвращаемым маршрутизатором:

csharpprivate static void Respond(HttpListenerResponse response, ResponsePacket resp)
{
  response.ContentType = resp.ContentType;
  response.ContentLength64 = resp.Data.Length;
  response.OutputStream.Write(resp.Data, 0, resp.Data.Length);
  response.ContentEncoding = resp.Encoding;
  response.StatusCode = (int)HttpStatusCode.OK;
  response.OutputStream.Close();
}
Примечание: здесь становится ясно, что фактическое расположение файла «контента» сервер может полностью подделывать. Автор положил весь HTML-контент в папку Pages и таким образом подделывает корневое расположение. Можно делать и другое — загружать данные из базы данных, связываться с другим сервером, динамически генерировать страницу из данных... Все это возможности, которые исследуются по мере развития базовой раздачи контента.

Шаг 4 — Дьявол в деталях

Страницы ошибок

Добавим несколько страниц ошибок (даже если сейчас используем не все):

  • Истёкшая сессия
  • Нет авторизации
  • Страница не найдена
  • Ошибка сервера
  • Неизвестный тип

Чтобы программа могла определить, где находятся страницы для каждой ошибки, добавим серверу enum:

csharppublic enum ServerError
{
  OK,
  ExpiredSession,
  NotAuthorized,
  FileNotFound,
  PageNotFound,
  ServerError,
  UnknownType,
}

Теперь начнём обрабатывать ошибки (без бросания исключений). Сначала — неизвестное расширение:

csharpif (extFolderMap.TryGetValue(ext, out extInfo))
{
 // ...
}
else
{
  ret = new ResponsePacket() { Error = Server.ServerError.UnknownType };
}

И так далее. Для обработки ошибок используем callback, который может предоставить веб-приложение, — в виде страницы, на которую нужно направить пользователя:

csharpResponsePacket resp = router.Route(verb, path, kvParams);

if (resp.Error != ServerError.OK)
{
  resp = router.Route("get", onError(resp.Error), null);
}

Respond(context.Response, resp);

И прямой обработчик ошибок в веб-приложении:

csharppublic static string ErrorHandler(Server.ServerError error)
{
  string ret = null;

  switch (error)
  {
    case Server.ServerError.ExpiredSession:
      ret= "/ErrorPages/expiredSession.html";
      break;
    case Server.ServerError.FileNotFound:
      ret = "/ErrorPages/fileNotFound.html";
      break;
    case Server.ServerError.NotAuthorized:
      ret = "/ErrorPages/notAuthorized.html";
      break;
    case Server.ServerError.PageNotFound:
      ret = "/ErrorPages/pageNotFound.html";
      break;
    case Server.ServerError.ServerError:
      ret = "/ErrorPages/serverError.html";
      break;
    case Server.ServerError.UnknownType:
      ret = "/ErrorPages/unknownType.html";
      break;
  }

  return ret;
}

Разумеется, нужно инициализировать обработчик ошибок: Server.onError = ErrorHandler;

Редиректы

Вы замечаете: URL в сообщениях об ошибках выше не меняется при показе страницы. Это потому, что редиректа в ответе нет. Время исправить это: будем считать, что обработчик ошибок всегда ведёт нас на другую страницу, поэтому меняем способ управления ответом. Вместо получения нового ResponsePacket и отправки этого контента браузеру ставим свойство Redirect на страницу, на которую хочет перейти веб-приложение. В целом это становится универсальным механизмом редиректа:

csharpif (resp.Error != ServerError.OK)
{
  resp.Redirect = onError(resp.Error);
}

И небольшой рефакторинг метода Respond:

csharpprivate static void Respond(HttpListenerRequest request, HttpListenerResponse response, ResponsePacket resp)
{
  if (String.IsNullOrEmpty(resp.Redirect))
  {
    response.ContentType = resp.ContentType;
    response.ContentLength64 = resp.Data.Length;
    response.OutputStream.Write(resp.Data, 0, resp.Data.Length);
    response.ContentEncoding = resp.Encoding;
    response.StatusCode = (int)HttpStatusCode.OK;
  }
  else
  {
    response.StatusCode = (int)HttpStatusCode.Redirect;
    response.Redirect("http://" + request.UserHostAddress + resp.Redirect);
  }

  response.OutputStream.Close();
}
Примечание: закрытие потока вывода очень важно. Если не закрыть его, браузер может ждать данных. И заметьте: поскольку ошибки обрабатываются редиректом, единственные два кода статуса, которые наш веб-сервер вообще может выдать, — это OK и Redirect.

Обработка исключений

Тот же механизм редиректа используем для перехвата настоящих исключений — оборачивая продолжение GetContextAsync в блок try-catch:

csharpcatch(Exception ex)
{
  Console.WriteLine(ex.Message);
  Console.WriteLine(ex.StackTrace);
  resp = new ResponsePacket() { Redirect = onError(ServerError.ServerError) };
}

Шаг 5 — Обзор и решение новых задач

Теперь имеем дело с глаголами, особенно с POST. Это позволит решить три следующих пункта списка.

Глаголы (Verbs)

С HTTP-запросом может приходить множество глаголов: OPTIONS, GET, HEAD, POST, PUT, DELETE, TRACE, CONNECT. По сути, веб-серверу нет дела до глагола — глагол лишь даёт дополнительную информацию о том, какой обработчик вызвать для ответа. Наконец мы добрались до того, чего автор до сих пор избегал, — контроллеров. Вместо того чтобы знать о паттерне Model-View-Controller или навязывать его разработчику веб-приложения, реализованный веб-сервер предоставляет простой механизм маршрутизации глаголов и путей к обработчикам. Только и всего. Обработчик в свою очередь решает, направить ли браузер на другую страницу или остаться на текущей.

Маршруты (Routes)

Начинаем с базового маршрутизатора, состоящего из класса Route:

csharppublic class Route
{
  public string Verb { get; set; }
  public string Path { get; set; }
  public Func<Dictionary<string,string>, string> Action { get; set; }
}

Заметьте: свойство Action — это функция-callback, принимающая параметры URL (с post-параметрами разберёмся позже) и ожидающая необязательный «URL редиректа».

csharppublic void AddRoute(Route route)
{
  routes.Add(route);
}

Теперь реализуем вызов специфичных обработчиков приложения — рефакторинг метода Route:

csharppublic ResponsePacket Route(string verb, string path, Dictionary<string, string> kvParams)
{
  string ext = path.RightOfRightmostOf('.');
  ExtensionInfo extInfo;
  ResponsePacket ret = null;
  verb = verb.ToLower();

  if (extFolderMap.TryGetValue(ext, out extInfo))
  {
    string wpath = path.Substring(1).Replace('/', '\'); // убираем ведущий '/' и форматируем разделителем пути Windows
    string fullPath = Path.Combine(WebsitePath, wpath);

    Route route = routes.SingleOrDefault(r => verb == r.Verb.ToLower() && path == r.Path);

    if (route != null)
    {
      // у приложения есть обработчик для этого маршрута
      string redirect = route.Action(kvParams);

      if (String.IsNullOrEmpty(redirect))
      {
        // отвечай загрузчиком контента по умолчанию
        ret = extInfo.Loader(fullPath, ext, extInfo);
      }
      else
      {
        // отвечай редиректом
        ret = new ResponsePacket() { Redirect = redirect };
      }
    }
    else
    {
      // пробуем поведение по умолчанию
      ret = extInfo.Loader(fullPath, ext, extInfo);
    }
  }
  else
  {
    ret = new ResponsePacket() { Error = Server.ServerError.UnknownType };
  }

  return ret;
}

Теперь изменим демо-страницу: по клику кнопки она делает POST-запрос к серверу, и в нашем обработчике мы перенаправляемся на другую страницу. Да, это можно было сделать целиком на JavaScript, но здесь мы показываем обработчики глагол-путь, поэтому реализуем поведение на стороне сервера.

Также добавляем разбор входного потока запроса в пары ключ-значение и логирование параметров (и URL, и параметров входного потока):

csharpprivate static async void StartConnectionListener(HttpListener listener)
{
  // ...
  Dictionary<string, string> kvParams = GetKeyValues(parms); // преобразуй в пары ключ-значение
  string data = new StreamReader(context.Request.InputStream, context.Request.ContentEncoding).ReadToEnd();
  GetKeyValues(data, kvParams);
  Log(kvParams);
  // ...
}

private static Dictionary<string, string> GetKeyValues(string data, Dictionary<string, string> kv = null)
{
  kv.IfNull(() => kv = new Dictionary<string, string>());
  data.If(d => d.Length > 0, (d) => d.Split('&').ForEach(keyValue => kv[keyValue.LeftOf('=')] = keyValue.RightOf('=')));

  return kv;
}

private static void Log(Dictionary<string, string> kv)
{
  kv.ForEach(kvp=>Console.WriteLine(kvp.Key+" : "+kvp.Value));
}

Смешивать URL-параметры и postback-параметры в одном наборе пар ключ-значение, может, и дурная привычка, но пока довольствуемся этой «более простой» реализацией.

Создаём новую HTML-страницу /demo/redirect с формой, идущей на /demo/redirect методом post, и кнопкой «Redirect Me» с именем redirectButton. Если присмотреться, в логе сначала виден GET при загрузке страницы, затем по клику на кнопку — POST с параметрами. Интересное в написании собственного веб-сервера — то, что действительно получаешь более глубокое ощущение того, что происходит за кулисами.

Теперь регистрируем обработчик для этого глагола и маршрута:

csharpstatic void Main(string[] args)
{
  string websitePath = GetWebsitePath();
  Server.onError = ErrorHandler;

  // регистрация обработчика маршрута:
  Server.AddRoute(new Route() { Verb = Router.POST, Path = "/demo/redirect", Action = RedirectMe });

  Server.Start(websitePath);
  Console.ReadLine();
}

public static string RedirectMe(Dictionary<string, string> parms)
{
  return "/demo/clicked";
}

Теперь по клику на кнопку нас перенаправляет. Это было легко. Минимальным рефакторингом решены три пункта:

  • Глагол всегда считался «get»
  • У приложения не было возможности манипулировать контентом (особенно HTML) после загрузки
  • Маршрутизацию нельзя было переопределить

Шаг 6 — Аутентификация и истечение сессии

На шаге 5 мы реализовали совсем базовый обработчик маршрута. Хочется чего-то более продвинутого, что обрабатывает вполне обычные вещи:

  • Убедиться, что пользователь имеет право видеть страницу
  • Проверить, не истекла ли сессия

Рефакторим callback-обработчики выше, чтобы они использовали класс Routing, который предоставляет встроенное поведение и позволяет разработчику веб-приложения заменять или дополнять своё (например, ролевую аутентификацию).

Управление сессиями

Сначала добавим базовые классы Session и SessionManager:

    /// времени истечения (в секундах).

    {
      return (DateTime.Now - LastConnection).TotalSeconds > expirationInSeconds;
    }
  }

  public class SessionManager
  {

    /// Отслеживает все сессии.

      sessionMap = new Dictionary<IPAddress, Session>();
    }

    /// Создаёт или возвращает существующую сессию для этого remote endpoint.
    /// </summary>

Добавим три класса, которые может использовать приложение:

  • AuthenticatedRouteHandler

csharpnamespace Clifton.WebServer
{
  /// <summary>
  /// Базовый класс обработчиков маршрутов.
  /// </summary>
  public abstract class RouteHandler
  {
    protected Func<Session, Dictionary<string, string>, string> handler;

    public RouteHandler(Func<Session, Dictionary<string, string>, string> handler)
    {
      this.handler = handler;
    }

    public abstract string Handle(Session session, Dictionary<string, string> parms);
  }

  // AuthenticatedRouteHandler и AuthenticatedExpirableRouteHandler
  // наследуют RouteHandler и реализуют управление состоянием Authorized
  // и истечением сессии в своём методе Handle.
}

И пример регистрации аутентифицированного обработчика:

csharpstatic void Main(string[] args)
{
  string websitePath = GetWebsitePath();
  Server.onError = ErrorHandler;

  // зарегистрируй аутентифицированный обработчик маршрута:
  Server.AddRoute(new Route() { Verb = Router.POST, Path = "/demo/redirect",
                                Handler = new AuthenticatedRouteHandler(RedirectMe) });

  Server.Start(websitePath);
  Console.ReadLine();
}
Почему класс, а не attribute? Автор ещё с первых дней работы с C# говорит: attribute хороши, чтобы подсказывать сериализатору, как сериализовать поля; в остальном они чаще поощряют плохой дизайн. Например, маршруты, написанные с базовым классом Route и дочерним классом AuthenticatedRoute, реализуются классами. Если нужна ролевая аутентификация, создаёте производный класс, а не вешаете attribute на часто пустые функции контроллеров.
